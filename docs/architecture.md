# 架构说明

## 运行边界

codex-switch 是按需运行的 Go 命令行程序。交互界面使用 Bubble Tea，命令与界面共用账户管理引擎；配置解析使用 go-toml，凭据密钥存入 macOS Keychain。

程序不常驻，不代理模型流量，不提供协议转换，也不管理其他客户端。官方登录、认证核验、官方额度查询和会话副本通过原生 Codex CLI 完成。切换结束后由用户手动启动客户端。

## 模块划分

| 位置 | 职责 |
| --- | --- |
| `cmd/codex-switch` | 子命令、帮助、交互菜单、编辑器和取消操作 |
| `internal/switcher/engine.go` | 账户启用、快照、事务与恢复 |
| `storage.go`、`backup.go` | 加密存档、锁、原子写入与密码备份 |
| `config.go`、`features.go`、`import.go`、`models.go` | TOML 导入、配置补丁和模型目录 |
| `runtime.go`、`processes.go`、`process_scope_darwin.go` | 客户端退出、进程范围判定和原生 CLI 调用 |
| `reauth.go`、`native.go` | 官方重认证、隔离进程与 RPC |
| `usage*.go` | 官方额度、第三方模板及缓存 |
| `sessions.go`、`session_titles.go` | 会话筛选、标题和原生副本 |
| `audit.go`、`maintenance.go`、`diagnostics.go` | 日志轮转、维护与只读诊断 |

## 切换事务

一个账户库绑定一个 Codex 目录，写操作通过文件锁串行执行。切换检查未完成事务、目录与当前认证归属；保存当前官方凭据，必要时刷新目标官方认证，再停止关联客户端。

配置和认证不能通过一次文件替换同时提交。引擎先持久化加密事务记录，逐一原子替换 `config.toml` 与 `auth.json`，使用原生 CLI 核验，然后保存账户状态并清理事务。普通失败尝试回滚；不能确认恢复完成时保留记录供 `recover` 处理。

单文件写入使用临时文件、同步、重命名与目录同步。重命名后的同步失败被单独识别，避免将已替换的数据误判为未写入。已提交但日志失败会报告警告，不用旧配置覆盖成功提交。

官方刷新可能轮换 refresh token。新凭据先保存到加密库；若未写入当前认证即取消，待同步标记阻止旧认证覆盖它。下次切换使用最新保存的凭据。

## 配置与会话

官方 provider 标识为 `openai`，第三方统一使用 `codex_switch`。导入时读取样例中实际选择的 provider 表，再转换为受控账户配置；不执行来源中的认证命令。

配置补丁修改账户相关字段，保留无关 TOML 内容；重复应用应保持幂等，避免空行累积。模型和额度配置按账户保存。账户存档是加密格式，不支持直接手工编辑；当前生效的 Codex 配置仍为普通 TOML。

会话跨 provider 接续通过原生 `thread/fork` 创建新会话，不改写旧 rollout 文件。候选筛选以 provider 为单位，而非账户备注。副本创建后仍受目标上游对历史内容的兼容性约束。

## 数据保护与进程控制

账户库、额度缓存及事务记录使用 AES-256-GCM；随机密钥保存到 Keychain，并与存储路径关联。密码备份使用独立盐值与 PBKDF2-HMAC-SHA256 派生密钥。目录为 700，凭据文件为 600。

当前 Codex 认证及直接 bearer 配置必须供客户端读取，因此落盘仍含凭据。加密存档不保护已经解锁的客户端或同一用户权限下的其他程序。

强制切换只终止能确认归属的 Codex 任务。执行前重新核对 PID、进程身份及目录范围；未知归属、工具祖先进程或持续重启等情况停止操作，不扩大到整个 IDE 或系统。

日志只记录标识、阶段及固定错误码，不保存原始错误、配置或认证内容。备份和账户库不应放入 Git。

## 资源与兼容性

没有后台定时额度轮询。账户列表和详情进入时请求一次，可手动刷新；官方查询不承担后台凭据续期。会话列表使用分页和有界候选集合，标题扫描读取有限范围；TOML/JSON 导入限制 1 MiB，本地受保护文件限制 8 MiB，模型目录最多 200 项。

网络请求与子进程有超时和取消路径，交互取消等待必要清理后返回。原生 Codex RPC、模型目录格式、图片授权及进程识别会受到上游版本变化影响，需要在支持版本上重新验收。

Go 单文件构建满足当前 CLI 的分发需求。未来 GUI 可复用管理引擎；是否引入 GUI 框架或迁移 Rust，应在需要具体桌面能力时单独评估，避免给 CLI 增加常驻服务与运行时负担。
